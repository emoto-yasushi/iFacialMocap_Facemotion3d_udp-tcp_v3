# Face Motion v3 — Python2本の通信サンプル

**iFacialMocap・iFacialMocapTr・Facemotion3dから、BlendShapeと頭・左右の目の数値をUDPまたはTCPで受信します。**

[English](README.md) ／ [MITライセンス](LICENSE)

## 1. まず通信する — 実際のiPhone／iPadから受信

**Python 3.10以上。`pip install`は不要です。** 実機から受信する場合は、**`face_motion_v3.py`の1本だけ**を使います。このファイルのあるフォルダでターミナルを開いてください。**模擬送信プログラムは起動しません。** Macで`python`が動かなければ、`python3`に置き換えます。

`PHONE_IP`をiPhone／iPadのLAN内IPアドレスに置き換え、**UDP・TCPのどちらか1つを実行**してください。

```sh
# UDP
python face_motion_v3.py --host PHONE_IP --transport udp

# またはTCP
python face_motion_v3.py --host PHONE_IP --transport tcp
```

**iFacialMocapTrも同じコマンドです。Facemotion3dでは「Other」ライセンスが必要で、`--app facemotion3d`を追加します。** Facemotion3dの他のライセンスでは、このサンプルとの通信はできません。

開始要求HELLOとUDPの対応表ACKは受信プログラムが自動で処理します。通常のTCPでは、アプリ層の対応表ACKは不要です。

**成功の目印：** `State=STREAMING`が出て、`frames=`の数が増えます。約1秒に1回、1フレームの**全項目**を1行で表示します。受信・解析は正常な各フレームで行い、表示だけを間引きます。ターミナルの幅によっては見た目が折り返されます。終了は**Ctrl+C**。`--log-every 0`は値の表示だけを止める指定です。

### 対応アプリと最低バージョン

| アプリ | 対応バージョン |
|---|---|
| **iFacialMocap** | **1.5.3以降** |
| **iFacialMocapTr** | **1.2.6以降** |
| **Facemotion3d** | **1.4.6以降** |

**このサンプルは、上記の各バージョン以降のアプリのみ対応しています。それ以前のバージョンには対応していません。** 最低バージョン未満のアプリをお使いの場合は、アプリを更新してから実行してください。

iOSアプリは、**標準ポートのFMV3 `contract_revision = 4`** に対応している必要があります。このサンプルは**v3専用**で、旧v1/v2の文字列データの解析や自動切替は行いません。

## 2. iPhoneなしで試す — ターミナルを2つ使う

| ファイル | 使う場面 |
|---|---|
| **`face_motion_v3.py`** | 受信プログラム。**実際のiPhone／iPadと通信するなら、この1本だけで動きます。** |
| **`simulate_ios_v3.py`** | iPhoneなしで試すための模擬送信プログラム。使う場合は、上の受信ファイルと同じフォルダへ置きます。 |

**同じフォルダでターミナルを2つ開き、次の順番で起動**してください。

**ターミナル1：iPhoneの代わりに合成データを送信**

```sh
python simulate_ios_v3.py --transport udp --port 51083 --count 52 --change-after 0
```

**ターミナル2：そのデータを受信**

```sh
python face_motion_v3.py --host 127.0.0.1 --transport udp --port 51083
```

TCPを試す場合は、**両方のコマンドの`udp`を`tcp`に変更**します。終了するときは、**両方のターミナルでCtrl+C**を押してください。

`127.0.0.1`は同じPCを指します。**51083は模擬送信だけのテスト用ポートであり、iOSの標準ポートを変更したわけではありません。** 同じPC上の送信・受信で待受ポートが衝突しないように指定しています。受信側のローカルポートは通常どおりUDP49983／手動TCP待受49986です。

この例では**52項目の合成データ**を送ります。ARKitの標準52項目を忠実に再現するものではありません。`jawOpen`は変化し、ほかの多くの値は意図的に固定しています。`count=52`で受信数を確認できます。`--change-after 0`は対応表の変更を無効にする指定です。この指定を外すと、既定では30フレーム送信後に独自項目が1つ増えます。

模擬送信は**iOS／ARKitのエミュレーターではなく、カメラも使いません。** ACK待ち・再送処理はファイル内へ統合済みで、`schema_delivery.py`は不要です。

## 3. iOSのIP手入力モードから送信する

まずPCを待機させ、その後iOSアプリのv3手動送信で、**PCのLAN内IPと受信ポート**を指定します。

```sh
python face_motion_v3.py --listen --transport udp   # PCのUDP49983へ送信
# または
python face_motion_v3.py --listen --transport tcp   # PCのTCP49986へ接続
```

`0.0.0.0`を送信先IPとして入力しないでください。UDPは対応表にACKを返し、TCPはアプリ層ACKなしで接続を使います。復旧の再試行を使い切っても、PCは受信待機を続けます。

| アプリ | iOS側UDP | PC側UDP | iOS側の直接TCP待受 | PC側の手動TCP待受 |
|---|---:|---:|---:|---:|
| iFacialMocap / iFacialMocapTr | 49983 | 49983 | 49984 | 49986 |
| Facemotion3d | 49993 | 49983 | 49994 | 49986 |

`--port`はiOS／模擬送信側の接続先、`--listen-port`は受信プログラムのローカルポートです。通常TCPではPCから張った1本の接続で送受信します。PC49986は手動接続の受入用で、通常通信の返答用に2本目の接続を張るという意味ではありません。

同じローカルポートで受信プログラムを二重起動しないでください。Facemotion3dでは「Other」ライセンスが必要で、受信コマンドに`--app facemotion3d`を追加します。

## 4. 自分のプロジェクトで値を使う

`face_motion_v3`から`V3Client`を読み込み、**ログ文字列を解析せず、コールバックの数値を使います。** 対応表を受け取ったときに項目の位置を調べ、各フレームではその位置から値を取り出します。

```python
from face_motion_v3 import V3Client

jaw_index = None

def on_schema(schema):
    global jaw_index
    jaw_index = schema.index_by_name.get("jawOpen")

def on_frame(frame):
    if jaw_index is not None and frame.tracking:
        jaw = frame.blend_values[jaw_index] / 100.0
        # jawを自分の描画処理へ渡す。受信ループを長時間止めない。

V3Client("PHONE_IP", transport="udp").run(on_frame, on_schema=on_schema)
```

項目数は**52固定ではありません**。名前は`frame.schema.blend_names`、同じ順番の全値は`frame.blend_values`、頭と目は`frame.head`・`frame.right_eye`・`frame.left_eye`です。負値も扱い、`-25`は係数`-0.25`に相当します。受信段階で負値や100超を切り捨てません。`.run()`は呼び出したスレッドを使い続けるため、GUIへの統合では受信と画面更新のスレッドを適切に分けてください。

Facemotion3d（「Other」ライセンス）では、`V3Client`に`app="facemotion3d"`を渡してください。iFacialMocapTrは既定のアプリ設定を使います。

## 背景：v3を作った経緯

従来の**v1/v2はテキスト形式**で、各フレームに項目名と値を文字列として含めて送信します。受信データをそのまま読めるため、内容を確認しやすく、基本的な受信処理も比較的単純に実装できます。

v3を作るきっかけは、組み込み開発者から寄せられた「描画よりも、受信した文字列の解析にCPU時間を使っている」という相談でした。目的は、繰り返し行う文字列解析と項目名の送信を減らし、アプリ本来の処理に使える余力を増やすことです。受信プログラム全体の実装を単純にすることが目的ではありません。

v3では、**`SCHEMA`（対応表）で項目名・並び順・数値型を伝え、その後の`FRAME`の本文には、その順序でバイナリの数値を送ります。** 受信側は対応表の受信・更新時に名前と配列位置を対応付けるため、各フレームで文字列の分割・名前の検索・文字列から数値への変換を繰り返す必要がありません。順序が固定されるのは**その対応表の中だけ**で、項目の追加・変更にも対応し、52個固定ではありません。

## v1/v2とv3の使い分け

[iFacialMocap公式サイト：v1/v2の通信仕様](https://www.ifacialmocap.com/for-developer/)

| 比較する点 | v1/v2：テキスト形式 | v3：対応表＋バイナリ数値 |
|---|---|---|
| 受信データの確認 | 文字列から項目名と値を直接読めます。 | 対応表に従ってバイナリを復元します。このサンプルでは復元後の値を表示します。 |
| 基本的な受信処理の実装 | 小さなスクリプトや試作では、より直感的に始めやすい方式です。 | 対応表の管理、バイナリの検証、通信方式に応じた制御など、実装する処理が増えます。 |
| 継続受信時の処理 | 各フレームで項目名を送り、文字列を数値へ変換します。 | FRAME本文に項目名を繰り返さず、各フレームの文字列解析を省けます。 |
| 継続通信時の帯域負担 | 各フレームで項目名と文字列の数値を繰り返し送ります。 | 同じ項目数・フレームレートなら、通常はモーションデータのバイト数を削減できます。 |
| 向いている用途 | データを目視しながらの開発、単純な連携、解析負荷や通信量が問題になっていない既存プロジェクト。 | 組み込み受信機、独自の描画処理、継続的な通信などで、解析のCPU負荷や通信量が問題になっている用途。 |

**v3は選択肢を増やすための方式であり、動作しているv1/v2の連携を必ず移行する必要はありません。** バイナリの効率より、コードの単純さやデータの読みやすさを優先した方がよい場合もあります。このリポジトリの実装は**v3専用**で、v1/v2の解析や自動切替は行いません。既存のv1/v2受信プログラムでv3を受信するには、v3への対応が必要です。

### モーションデータの小型化と通信帯域への負担軽減

同じ項目を同じフレームレートで継続送信する一般的な条件では、**v3のバイナリのモーションフレームは、相当するv1/v2の文字列フレームより小さくなります。** そのため、送受信するモーションデータ量を減らし、通信帯域への負担も抑えられます。項目名や数値型は対応表で伝え、FRAMEごとには繰り返し送りません。

例えば、**52個のBlendShapeを`i16`で送る場合、分割されていないFMV3のFRAMEは192バイト**です（ヘッダー40＋BlendShape値104＋頭・目の値48バイト）。60フレーム／秒なら、**FRAMEだけで11,520バイト／秒（11.52 kB/s）**になります。これは[通信仕様のデータ構造](PROTOCOL_V3_JA.md)からの計算値で、性能を実測したベンチマークではありません。

ネットワークのヘッダー、対応表の送信・更新・再送、ACKやPING/PONGなどの制御通信は別途必要です。削減量は項目名・文字列の表記・項目数・通信時間などによって変わるため、**すべてのメッセージや短時間の通信で必ず小さくなるという意味ではありません。** 通信量の削減が、遅延の短縮や特定のフレームレートを保証するものでもありません。

### 組み込み環境で利用する場合

v3は、各フレームで繰り返す処理を減らすことで、リソースに制約のある受信環境にも役立ちます。ただし、**総メモリ使用量や実装サイズが必ず小さくなること、すべての機器で特定のフレームレートを達成できることを保証するものではありません。** 対応表の解析・保持、受信・再構成用バッファ、検証、対応表の更新、UDPでの対応表ACKなどの通信制御は必要です。対象機器でCPU負荷とメモリ使用量を確認してください。

Pythonファイルは**参照実装と動作確認用のツール**であり、組み込み機器でPythonを動かすことが必須ではありません。[通信仕様書](PROTOCOL_V3_JA.md)に従い、C・C++など、対象環境に合う言語でも実装できます。通信制御の実装が増えても各フレームの処理負荷を減らしたい場合はv3、実装サイズやデバッグのしやすさを重視する場合はv1/v2、という観点で選んでください。
